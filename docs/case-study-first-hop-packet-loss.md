# 案例：第一跳丢包，到底是 CPU 还是线路

一次故障定位的记录。方法不限于光猫，路由器、软路由、虚拟化转发都能套。

## 现场

```
光纤 ──► 光猫（路由模式，PPPoE + NAT）──► 软路由（N4100 / PVE，二次 NAT）──► 终端
```

九联 UNG953H1-S，XGPON，1 个 2.5G 口加 3 个千兆口，没有 WiFi。1000 Mbps 宽带，
光猫常年待在弱电箱里，75 到 78 度。

| 指标 | 数值 |
| --- | --- |
| 下行峰值 | 114 MB/s，约 912 Mbps |
| 下行常态 | 60 MB/s，约 480 Mbps |
| `ping` 光猫网关 | 丢包 5% |
| `ping` 公网 | 丢包 4% |

峰值 912 Mbps 几乎贴着千兆口的物理上限（约 940，扣掉 TCP 和 PPPoE 开销）。链路是通的，
问题不是带宽不够。

## 三步定位

**一、ping 网关丢包，跟运营商没关系。** 报文在设备内部完成二层转发就回来了，不经过 PON
口，不上 OLT。所以第一跳丢的 5%，运营商不背这个锅。

**二、公网 4% 比网关 5% 还低。** 如果外网有额外丢包，总丢包率必然高于第一跳。实测反而
更低，差的 1% 在噪声范围内。PON 侧、OLT、骨干都没问题，丢包全在第一跳。

**三、5% 丢包和 480 Mbps 同时成立，这才是重点。** 这 5% 如果真随机丢在 TCP 数据面上，
按拥塞控制模型，窗口刚涨起来就被砍半，单流吞吐会被压到百兆以下。而链路误码是无差别的，
TCP、ICMP、ARP 一律按比例丢。

实测是数据面还凑合、控制平面已经饿死。这个组合只有一种解释：丢的不是线上的包，是 CPU
来不及处理的包。

## 怎么区分

| 看什么 | CPU 过载 | 链路误码 |
| --- | --- | --- |
| 丢包分不分协议 | 分，ICMP 先被丢 | 不分，按比例丢 |
| 丢包对吞吐的影响 | 不成比例 | 强相关，吞吐崩 |
| 峰值能不能到线速 | 能，维持不住 | 一般到不了 |
| CRC / FEC 计数 | 不涨 | 一直涨 |
| 温度、CPU 占用 | 偏高 | 正常 |
| 换线、换口之后 | 没变化 | 会好转 |

CRC / FEC 计数最硬，这是硬件统计的。不涨就说明线上没有误码，网线、水晶头、光衰这一整类
原因可以一次性排除。

## 结论

光猫 CPU 长期卡在临界点，转发能力在 480 到 912 之间飘，ICMP 应答被扔掉。往上叠的因素：
路由模式下 PPPoE、NAT、防火墙、DHCP、TR-069 全走软转发；定制固件多挂了一套 Java OSGi
插件框架；弱电箱里 75 到 78 度一直在降频。

桥接是冲着根因去的。光猫退化成纯光电转换，CPU 负载掉一个量级，数据面走硬件转发。验收
别看测速，看 ping 网关的丢包有没有归零，这个指标比测速诚实。

| 指标 | 桥接前 | 桥接后 |
| --- | --- | --- |
| `ping` 网关丢包 | 5% | 0% |
| 下行常态 | 480 Mbps | 900–940 Mbps |
| 下行峰值 | 912 Mbps | 940–1100 Mbps |

峰值能不能过 940，看运营商实际放了多少量，跟设备无关。

## 几点补充

测速工具要先排除。Steam、迅雷的速率受 CDN 节点、分块策略、本地解压和磁盘 IO 影响，当
带宽测量会骗人，换多线程 `iperf3` 或运营商测速。另外分时段再测一遍：凌晨正常、晚高峰
拉胯，那是 PON 口超售，跟设备无关。

## 跟这个仓库的关系

上面这个案例就是 `decrypt-lastgood` 的起点。定位到根因之后，改桥接需要超级管理员权限，
而超密已经被 TR-069 刷成随机值了。

顺带一句：如果你正在向运营商主张设备不达标，自己先把配置改了，售后立场会变弱。先走报修
和换机流程，再考虑自己动手。
